# 校园资料智能问答助手 —— 需求调研

> 项目名称：基于 RAG 的校园资料智能问答助手
> 调研时间：2026 年 9 月
> 调研成员：李政达（组长）、谭存林、王皓阳、高星晨

---

## 一、项目背景

大语言模型（LLM）虽然知识面广、表达能力强，但存在一个公认的短板——**"幻觉"问题**：模型有时会一本正经地编造不存在的答案。尤其是涉及某一所学校的**具体政策**时（比如"我们学校图书馆一次能借几本书""校园卡丢了去哪补办"），通用大模型因为训练数据里没有本校的详细资料，往往答错、答偏或编造。

与此同时，校园里的各类信息（选课流程、图书馆规则、校园卡使用、宿舍报修等）分散在**教务处通知、图书馆官网、微信公众号、学生手册**等不同地方，学生（尤其是新生）查找起来费时费力，经常要翻半天才能找到一条准确的说明。

这两点矛盾，正好可以用 **RAG（检索增强生成，Retrieval-Augmented Generation）** 技术来解决：**先从本地校园资料里"检索"出和问题相关的内容，再把这些内容交给大模型"生成"回答**。这样回答就有了"依据"，不再是凭空生成。

本项目的定位：用一个网页，让学生输入问题，系统基于本地校园资料库给出**准确、有据可查**的回答，同时支持多轮追问。

---

## 二、项目目标

### 2.1 总体目标

构建一个**基于 RAG 的校园资料智能问答网页应用**：用户输入问题 → 系统从本地校园资料中检索相关片段 → 交给大模型生成有依据的回答。

### 2.2 可衡量的具体目标

| 编号 | 目标 | 衡量标准 |
|---|---|---|
| G1 | 回答准确（资料范围内） | 对已入库资料中的问题，回答准确率 ≥ 90% |
| G2 | 不胡说 | 资料里没有的内容，明确说"未找到"，不编造 |
| G3 | 响应快 | 单次问答响应时间 ≤ 5 秒 |
| G4 | 支持多轮对话 | 至少保留最近 5 轮对话上下文 |
| G5 | 资料可扩展 | 新增 txt 资料后，重建索引即可纳入回答 |
| G6 | 部署简单 | 本地一条命令即可启动，无需复杂配置 |

## 三、同类产品调研

> 调研方式：试用官网/开放产品、查阅产品文档、对照课程 PPT（Part 1 提到 Cherry Studio / ima 等无代码平台）。

### 3.1 调研记录

#### 产品 1：通用大模型（DeepSeek / 文心一言 / ChatGPT）

- **类型**：通用对话大模型
- **体验**：问"校园卡怎么充值"，会给出一个"通用"的答案，但具体到"我们学校的圈存机在食堂几楼、工本费多少"，基本答不对或直接编。
- **优点**：知识面广、表达流畅、开发门槛低（有现成 API）。
- **缺点**：**不了解本校具体政策**；会**幻觉**（编造）；无法保证答案可追溯。
- **对本项目的启发**：大模型负责"会说话"，但"知识"必须来自本地真实资料。

#### 产品 2：高校"校园百事通 / 智能客服"

- **类型**：各校官网或公众号里的问答机器人
- **体验**：回答精准，但往往是**关键词/规则匹配**，问法稍微变一下（同义改写）就答不上来。
- **优点**：答案准、基于本校知识库、可控。
- **缺点**：多为**规则匹配**不够智能；知识库需要**人工逐条维护**，维护成本高。
- **对本项目的启发**：要"准"，但不能只靠关键词匹配，要用语义检索（向量检索）来理解问法变化。

#### 产品 3：无代码知识库平台（Cherry Studio / ima / Coze）

- **类型**：拖拽式搭建智能体/知识库的平台（老师 PPT Part 1 里讲过的内容）
- **体验**：上传文档、点几下就能做出一个问答助手，速度快。
- **优点**：上手快、不用写代码、适合快速原型。
- **缺点**：本项目是**课程实训**，考核要求**用代码实现**（LangChain + FastAPI），体现所学知识点；无代码平台无法展示编程能力。
- **对本项目的启发**：产品形态可以借鉴（上传资料→问答），但**实现方式要用代码**。

#### 产品 4：商业 RAG 问答产品（智能文档助手 / 企业知识库）

- **类型**：成熟的 RAG 商业方案
- **体验**：效果好、功能全（支持多种文档、引用来源、权限）。
- **优点**：RAG 方案成熟、工程化程度高。
- **缺点**：多为**收费/部署重**，超出课程实训范围。
- **对本项目的启发**：RAG 的**核心链路**（加载→切分→向量化→存储→检索）是通用标准，我们按这个链路实现一个精简版即可。

### 3.2 对比总结表

| 产品 | 准确性 | 智能化 | 开发成本 | 是否需代码 | 适合本项目 |
|---|---|---|---|---|---|
| 通用大模型 | 低（有幻觉） | 高 | 低 | 否 | 仅作生成引擎 |
| 校园智能客服 | 高 | 低（规则匹配） | 中 | 否 | 借鉴"本地知识库"思路 |
| 无代码平台 | 高 | 中 | 低 | 否 | 形态借鉴，不用 |
| 商业 RAG 产品 | 高 | 高 | 高 | 否 | 借鉴核心链路 |
| **本项目（RAG）** | **高** | **高** | **低** | **是** | ✅ 采用 |

## 四、调研发现（结论）

1. **RAG 是解决"大模型不了解特定领域知识"的主流方案**——用"本地资料 + 向量检索 + 大模型生成"三者结合，兼顾了准确性和智能性。
2. **校园场景适合离线向量库**——校园政策更新不频繁，资料可以提前一次性向量化存储到本地 Chroma，检索时无需联网数据库。
3. **检索用"语义相似度"而非"关键词"**——用 embedding 向量做相似度检索，能理解"充值方式"和"怎么充钱"是同一个意思。
4. **必须做"幻觉控制"**——在提示词里明确要求模型"只按参考资料回答，资料没有就说没有"，这是本项目区别于普通聊天机器人的关键。
5. **技术选型有现成、且和课程对应**——LangChain 提供了完整的 RAG 工具链，正好对应老师 PPT 的 Part 6，用代码实现能完整体现课程所学。

## 五、核心需求

### 5.1 用户角色

| 角色 | 描述 | 典型问题 |
|---|---|---|
| 学生（主要用户） | 在校学生，查校园流程 | "校园卡怎么充值？""图书馆能借几本？" |
| 新生 | 不熟悉校园 | "选课怎么选？""宿舍报修找谁？" |
| 访客/家长 | 想了解学校信息 | "图书馆开放时间？" |

> 说明：本项目为课程实训，**不涉及登录注册**，任何打开网页的人都能提问。

### 5.2 功能需求列表（FR）

| 编号 | 需求 | 说明 |
|---|---|---|
| FR-1 | 网页问答 | 用户在网页输入问题，系统返回回答 |
| FR-2 | RAG 检索 | 系统从本地资料库中检索和问题最相关的内容片段 |
| FR-3 | 大模型生成 | 把检索到的内容 + 用户问题交给大模型生成回答 |
| FR-4 | 多轮对话记忆 | 记住同一用户的上下文，支持追问（如先问"图书馆能借几本"，再问"那能续借吗"） |
| FR-5 | 幻觉控制 | 资料中没有的内容，明确回答"未找到"，不编造 |
| FR-6 | 资料加载与切分 | 读取 data/ 目录下的 txt 资料，切成合适大小的文本块 |
| FR-7 | 向量化与存储 | 把文本块转成向量，存入本地 Chroma 向量库 |
| FR-8 | 索引重建 | 资料更新后，可一键重建向量索引 |
| FR-9 | 接口服务 | 提供 HTTP 接口（POST /chat）供前端调用，并有 /docs 接口文档 |
| FR-10 | 密钥安全 | API 密钥通过 .env 管理，不写死在代码、不提交到 Git |

### 5.3 非核心（本期不做，列入后续迭代）

- 支持 PDF / Word 等更多文档格式
- 回答中标注"引用来源"
- 流式输出（打字机效果）
- 用户登录与权限管理
- 部署到云端服务器
